# Harness 风格工程实践约定

日期：2026-04-10

目标：

1. 将后续双仓开发固定为 Harness 风格的工程流程。
2. 优先保证开发可控、边界清晰、验证可重复。
3. 避免 AI 辅助开发把项目带回“边改边猜”的状态。

## 1. 核心原则

### 1.1 规范先行

先定义：

1. 事实来源
2. 职责边界
3. 输入输出
4. 验证方式
5. 回滚锚点

再进入实现。

### 1.2 单一主入口

每一条链路必须有主入口。

当前主入口约定：

1. 内核事实入口：linux-orangepi-rt
2. 镜像集成入口：[../../userpatches/customize-image.sh](../../../userpatches/customize-image.sh)
3. 当前规则入口：[README.md](../../current/README.md)
4. 热区导航入口：[hpw_change_hotspots_2026-04-10.md](../../current/hpw_change_hotspots_2026-04-10.md)

### 1.3 兼容壳显式标记

任何过渡实现都必须显式标记：

1. 是否为事实入口
2. 是否为兼容壳
3. 是否为 fallback
4. 是否允许新逻辑继续进入

### 1.4 小闭环推进

每轮只做一个主闭环：

1. 文档冻结
2. 结构整理
3. 单链路审计
4. 单点行为优化

### 1.5 先收敛结构，再收敛实现

当结构混乱时，优先做：

1. 入口收敛
2. 命名收敛
3. 目录收敛
4. 职责收敛

而不是先改代码行为。

## 2. 本项目中的落地方式

### 2.1 阶段一：流程优化

只允许改：

1. 文档
2. 工作区任务
3. 工作区设置
4. 开发入口

### 2.2 阶段二：工程优化

只允许改：

1. 说明性注释
2. 职责文档
3. 目录结构
4. 辅助任务
5. 不改变行为的工程整理

### 2.3 阶段三：行为优化

只有在前两阶段完成后，才允许修改：

1. runtime 行为
2. boot profile 同步行为
3. service enable/disable 行为
4. 镜像默认集成行为

## 3. 每轮开发的固定模板

1. 当前阶段：一 / 二 / 三
2. 当前热区：build / runtime / DTS / RT patch
3. 行为变更：否 / 是
4. 事实依据：当前规则文档 + 代码
5. 验证入口：任务或显式 timeout 命令
6. 回滚锚点：文件 + 提交点

## 4. 禁止事项

1. 不在没有热区定位时直接改代码。
2. 不在没有最小验证入口时改行为。
3. 不把 build 同步副本当作内核事实来源。
4. 不让兼容壳继续无边界膨胀。
5. 不在同一轮同时跨多个热区做行为修改。
