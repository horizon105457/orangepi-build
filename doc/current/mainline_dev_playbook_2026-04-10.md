# 主线开发执行手册

日期：2026-04-10

目标：

1. 用最小流程保证后续主线开发可控。
2. 不让开发继续陷入文档和框架扩张。
3. 在完成必要治理后，尽快回到主线任务。

## 1. 开发前只做 3 步

1. 看 [hpw_change_hotspots_2026-04-10.md](hpw_change_hotspots_2026-04-10.md) 选热区。
2. 看 [harness/registry/source_of_truth.md](../../harness/registry/source_of_truth.md) 确认事实来源。
3. 跑一次工作区预检任务。

## 2. 每轮开发只允许一个主目标

可选主目标：

1. build 集成问题
2. runtime 编排问题
3. 内核/DTS 问题
4. 局部行为优化

不要在同一轮同时混做：

1. build 仓脚本整理
2. runtime 行为修改
3. 内核仓修改
4. 整镜像构建验证

## 3. 默认执行顺序

### 如果是非行为性问题

1. 先改文档、配置、任务入口或注释。
2. 跑最小预检。
3. 只有确认需要时再进入代码。

### 如果是行为性问题

1. 先锁定热区。
2. 先锁定最小验证。
3. 只改一条链路。
4. 验证后立即收口，不顺手扩改。

## 4. 默认验证顺序

1. `Harness: preflight`
2. `Harness: gate-b audit pack`
3. `OPiBot: build kernel only (timeout)`
4. `OPiBot: build image (timeout)`

说明：

1. 不是每次都跑到第 4 步。
2. 大多数开发只需要前 1 到 2 步。

## 5. 当前可以认为已经完成的治理工作

1. 双仓职责边界已固定。
2. 可信文档入口已固定。
3. hpw 热区导航已固定。
4. Harness 契约、计划、审计和事实源入口已固定。
5. 主要技术债已被文档化。

结论：

可以回到主线开发，不需要继续扩展治理框架。

## 6. 只有满足以下情况时，才继续做治理工作

1. 新增主链路出现职责冲突。
2. 热区边界发生明显变化。
3. 当前任务入口无法支撑验证。
4. 新行为变更缺乏回滚锚点。

否则默认继续主线开发。
